# Jev 目录规模独立实验

测试当前全目录分批判断策略。10/50/100/300 个目录，每目录 100 条 1024 维随机向量。目录摘要为固定模板合成短文本；问题与四个相关目录固定，新增目录均不相关。使用真实 Jev API，每批最多 10 个目录，串行判断，概率选前四。

每档 3 次真实路由请求，按不同顺序交错规模；每次对全量与局部 SQL 向量检索预热，再交错各测 7 次，先取每次局部中位数，再取三轮中位数。复用实际 MemoryEngine._select_directories、_vector_rank 与 JevDirectorySelector。单线程 BLAS，SQLite 在本机临时文件中，表及向量索引支持选定目录过滤。

只测路由与 chunk 向量读取、点积及排序；不含向量生成、BM25、事实/归纳召回、原文读取、RRF、回答与评分。随机向量不用于评估检索质量。不调用 Jev 一侧没有外部模型调用费用，但仍有本地计算成本。

## 解释

每批固定十个目录，因此目录增加主要增加串行批次数，不能解释为单次 Jev 推理随全库规模变慢。单次调用时间含网络、排队、推理及可能的 SDK 内部重试。三次重复不足以给出可靠 p95 或服务端性能曲线。
本实验小规模下，局部向量读取确实更快，但节省的是毫秒，目录判断花费的是秒；当前全目录串行策略不具备端到端速度收益。不要将这个结论推广为目录路由永远无益，磁盘冷读、远程存储、更大单目录载荷和树状路由均未测试。
全部十二次试验成功，没有重跑失败项。四个合成相关目录在各次试验均入选（仅为链路检查，不是准确率评测）。
